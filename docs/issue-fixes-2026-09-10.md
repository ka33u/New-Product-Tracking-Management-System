## #2：新建项目白屏

新建项目的规格行 ID 只用于当前弹窗中的 React key、编辑定位与移除，提交前会排除，业务 ID 由服务端生成。因此改用弹窗内单调计数的临时行标识，不依赖 `crypto.randomUUID()`，也不改变服务端、安全令牌或会话的 ID 生成方式。

首行采用惰性、无副作用初始化；增加规格时在事件中生成新标识，状态更新函数保持纯函数。移除后再增加不会复用旧标识，普通重绘不会重新创建首行或改变已填写内容。

组件回归模拟 `crypto.randomUUID` 缺失，以及整个 `crypto` 缺失，执行真实新建窗口函数和回调；覆盖 Strict Mode 的重复初始化/状态更新、重绘、编辑、增删规格和提交排除临时 ID。这不是实际 Chrome/Edge 页面点击验收。

## #1：启动/退出保护

上游 [workers-sdk #5544](https://github.com/cloudflare/workers-sdk/issues/5544) 在 Windows 端口冲突时记录了相同的 `isClientError(syncRes.status)` 断言。该线索支持排查残留监听进程，但不能证明本 Issue 中的 Windows 主机一定是相同根因，也不能证明持久化 D1 损坏。

本机复测另外确认：当前 Miniflare 的 `exit-hook` 在 SIGINT/SIGTERM 中直接调用 `process.exit(130/143)`，其 workerd 清理是未等待的异步操作；旧入口在创建 Miniflare 后注册自己的异步信号处理，无法保证清理完成。最初的真实运行器信号测试因此以 130 提前结束，而不是真正完成重启验证。

正式启动器现将 Miniflare 放在 Node Worker 线程中，由不加载 Miniflare 的主线程接收控制台信号，通知运行线程执行并等待 `dispose()` 后退出。该设计利用 [Node Worker 不接收进程信号](https://nodejs.org/api/worker_threads.html#class-worker) 的边界，不修改依赖包或全局移除第三方监听器。新固定版本包含并校验线程入口；旧固定版本由外层线程启动器兼容加载，业务运行代码仍来自已验证的旧包。

- 创建运行器之前，只检查本次指定的 `127.0.0.1` 端口；有监听服务则明确报端口占用，不启动第二个 workerd，不终止原服务，不修改数据。端口为 0 的隔离测试继续由系统分配。
- 退出、启动失败和显式关闭共用一次清理操作，结束后移除本次信号监听器。Windows 额外处理控制台 `SIGBREAK`；不会将既有失败退出码改写为成功。
- 等待运行器启动后，仍完整读取 D1、执行增量迁移并校验已执行文件；仅全部成功后输出 `Ready on`。收到退出信号的启动流程不能再返回一个已关闭的实例。
- 数据库代理断言会附加排查旧服务的提示并保留原错误原因。迁移异常、迁移校验值不一致都继续拒绝启动，不提供“跳过迁移继续运行”的降级。

端口检查不是操作系统互斥锁；不要同时启动两份服务，尤其不能让不同端口的服务共用同一数据目录。强制结束父进程、断电、SQLite 被其他程序占用、第三方代理/防火墙拦截不在这些测试的完整保证范围内。程序不会自动搜索或批量杀死 workerd。

## 复测命令

先完成构建，再执行：

```sh
npm run test:issue-regressions
npm run test:restart-runtime
```

前者测试组件和启动清理；后者强制创建全新的临时数据目录，在同一端口三次启动，核对 D1 合成记录、R2 合成附件及迁移记录不变，覆盖重复启动拒绝、校验值损坏后拒绝启动及数据保留；另外启动真正的 `local-server.mjs` 两次，测试主进程等待线程停止后端口释放。POSIX 使用真实 SIGINT，Windows 自动测试使用仅父进程可发送的协作关闭消息；Windows 的 `child.kill()` 会强制终止，不能将它冒充 Ctrl+C 验收。不会读取或修改 `.wrangler/state` 中的现有业务数据。

当前开发主机为 macOS，不能据此声称 Windows Server 2022 / Windows 10、Node v24 或真实强杀后的行为已经通过。请在报错的 Windows 主机运行以上专项，再复测实际控制台停止后重启。若仍出现代理断言，应保留完整日志及当时的端口/PID 信息进一步定位，不删除数据或绕过迁移。

## 更新已有安装

1. 确认源码目录没有尚未保留的本地修改。停止原服务，核对原端口已无监听，按已有流程备份数据库和附件。
2. 更新源码并重新构建。继续使用原数据目录，不把空白目录替换成现有业务库。
3. 尚未启用固定版本的安装，按原入口启动；已启用固定版本的安装，需准备并验证新的候选版本，再显式切换和重启。只更新源码或重建 dist 不会替换旧的固定运行包，参见[固定版本说明](local-releases.md)。
4. Windows 有残留服务时，在任务管理器或系统端口工具中核对具体 PID、父子关系和程序路径，再停止确认属于本项目的进程树。不要批量结束全部 Node/workerd，也不要仅强杀父进程后立即反复启动。

此次修复未开放公网/局域网监听；仓库的正式入口仍仅监听 `127.0.0.1`，不新增 `--host 0.0.0.0` 参数。其他机器的自定义入口或反向代理需要单独核对。消除 HTTP 白屏不代表普通 HTTP 可以安全传输账户密码；共享访问应另行配置 HTTPS 和访问边界。
